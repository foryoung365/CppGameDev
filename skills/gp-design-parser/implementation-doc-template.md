# 功能实现文档模板

输出最终结果时，优先使用以下结构。可根据策划案复杂度合并小节，但不要缺少“版本识别结果”“本次变更摘要”“主体清单与职责边界”“主体交接索引”“待确认项”。

## 1. 版本识别结果

- 原始文档：文档名称或用户提供的标识
- 当前版本：识别出的最新版本号、日期或生效标识
- 版本变更记录摘要：版本记录区对当前版本的原始描述
- 当前版本色标：颜色名称、视觉表现形式、适用位置
- 删除线标记：如存在 `<del>...</del>`，说明其是否属于当前版本删除内容，以及是否需要转为移除项
- 识别说明：若存在歧义、低清截图、多个候选颜色，在此说明

## 2. 本次变更摘要

按条列出本次版本新增、修改、删除的核心点。每条至少包含：

- 变更类型：新增 / 修改 / 删除 / 待确认
- 变更对象：系统、玩法模块、界面元素、配置项、触发条件等
- 变更摘要：一句话说明本次改了什么
- 删除线处理：若来源为 `<del>...</del>`，注明“已制作，需移除”或“未制作，可忽略”
- 来源位置：章节、页码、表格名、流程图节点或截图区域
- 主体：该变更主要落在哪个实现主体

## 3. 功能目标与适用范围

- 功能目标：该功能需要解决什么问题
- 适用对象：玩家、角色、队伍、公会、活动阶段、服务器等
- 生效范围：常驻、活动期、特定地图、特定玩法模式等

## 4. 名词与对象定义

列出实现需要依赖的核心对象、枚举、状态和值域。若沿用旧规则，注明 `来源：背景沿用`。

## 5. 主体清单与职责边界

先列出策划案中出现的所有实现主体，并保持原始称呼，例如：

- 游服
- 战场服
- 数据服
- 客户端
- 配置表 / 后台

每个主体至少写清：

- 主体名称
- 主体职责边界
- 主体持有的数据
- 主体负责的判定 / 下发 / 持久化 / 展示
- 与其他主体的交互对象

若文档只写“服务端”但无法唯一映射到具体主体，必须在此标注为待确认，不要直接归并。

## 6. 核心规则

按主题拆分规则。若同一规则跨多个主体，必须继续按主体拆开写，不得混写为一条笼统“服务端处理”。

建议每条规则使用以下格式：

- 规则名称：
- 主体：
- 规则描述：
- 触发条件：
- 执行结果：
- 限制条件：
- 上游输入方：
- 下游通知方：
- 来源：本次变更 / 背景沿用 / 推断
- 备注：如有旧版差异、替换关系、`<del>...</del>` 删除线处理结论，在此补充；已制作的删除线内容应标注为需移除，未制作的删除线草案可忽略

## 7. 流程与状态变化

- 进入条件
- 状态流转
- 退出条件
- 失败回退
- 与其他系统的联动节点

必要时用编号流程描述，不必强制使用图。

若流程跨多个主体，建议写成：

1. 游服动作
2. 战场服动作
3. 数据服动作
4. 客户端动作

不要把多主体动作揉成一个步骤。

## 8. 数据、配置与持久化

- 配置表或配置项
- 默认值与取值范围
- 是否需要热更
- 持久化字段
- 重置时机
- 跨天、跨周、活动切期处理

建议额外写明每项数据“归属主体”。

## 9. 主体间接口、事件与通知

- 请求接口
- 响应字段
- 推送事件
- 条件校验失败的错误码或提示
- 与其他系统交互的输入输出
- 发起主体
- 接收主体

不要只写接口名；必须写清是谁发起、谁接收、谁落库。

## 10. 按主体拆分职责

不要使用笼统的“服务端”标题。改为按主体逐项写，例如：

- 游服：xxx
- 战场服：xxx
- 数据服：xxx
- 客户端：xxx

若存在共享逻辑、GM 指令、后台配置或日志埋点，也在此补充。

## 11. 边界与异常处理

- 条件不满足时如何处理
- 配置缺失或非法时如何处理
- 并发、重复触发、跨服或断线重连影响
- 旧数据兼容与版本切换影响

若异常处理涉及多个主体，也必须按主体拆开说明。

## 12. 验证关注点

- 正常路径
- 边界值
- 状态切换
- 回滚与重登
- 与旧规则兼容

## 13. 主体交接索引

这是给后续 agent / 程序员继续拆解时使用的索引，至少包含：

- 游服负责规则：
- 战场服负责规则：
- 数据服负责规则：
- 客户端负责规则：
- 配置侧负责项：

要求：

- 每条索引都指向本文中的具体规则名称或章节
- 不允许出现“服务端整体负责”这类笼统描述

## 14. 待确认项

对策划案中缺失、冲突、低置信度识别或只能推断的内容，逐条列出：

- 问题点
- 影响范围
- 当前暂定处理
- 需要策划确认的内容

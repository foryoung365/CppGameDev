# 策划案解析

处理对象：`$ARGUMENTS`

若用户未提供参数，则处理当前对话中用户明确指定的策划案文档、附件或截图。

目标不是摘要，而是将策划案中的“本次版本变更”和“背景规则”拆分、归并并重写为一份可供 gameplay 开发程序员直接编码的实现文档。

在组织最终输出前，先读取同目录文件 `implementation-doc-template.md`，按其中结构生成结果；若策划案较简单，可合并小节，但不得省略“版本识别结果”“本次变更摘要”“待确认项”。

默认将生成结果写入当前项目的 `docs/desgin/` 目录，而不只是输出在对话中。

- 若目录不存在，先创建 `docs/desgin/`。
- 输出文件名优先使用策划案原文件名，追加 `-功能实现文档.md` 后缀；若无法取得原文件名，则使用 `策划案解析-功能实现文档.md`。
- 若目标文件已存在，优先覆盖为最新整理结果；若用户明确要求保留历史版本，再改为时间戳命名。
- 在完成写入后，再向用户简要说明输出文件路径。

若输入是 PDF，优先使用同目录下的可执行工具 `bin/pdf-to-annotated-markdown.exe` 将 PDF 转为带颜色标注的 Markdown，再基于该 Markdown 识别版本色标与变更内容；不要直接把 PDF 纯文本抽取结果当作颜色判断依据。

- 标注稿默认输出到 `docs/desgin/<原文件名>-颜色标注.md`。
- 若 `bin/pdf-to-annotated-markdown.exe` 缺失或需要重建，可执行 `build-pdf-tool.ps1` 重新打包。
- 若 `.exe` 不可用，再退化为直接视觉理解与 PDF 文本抽取混合判断，并在结果中明确说明降级处理。

## 执行步骤

### 0. 预处理 PDF 色彩信息

- 当输入是 PDF 时，先执行：
  - `bin/pdf-to-annotated-markdown.exe --input "<pdf路径>" --output "docs/desgin/<原文件名>-颜色标注.md"`
- 将生成的颜色标注 Markdown 作为颜色识别的一等输入。
- 若标注稿中存在 `[color bg="..."]`、`[color fg="..."]` 或两者叠加标签，优先据此判断本次版本记录与正文的颜色对应关系。
- 对于标注稿无法完整覆盖的复杂页面，再补充直接视觉理解复核。

### 1. 锁定当前版本与版本色标

- 优先在标题下方、首页前部、目录前或封面后的版本变更记录区域查找最新版本。
- 依据明确版本号、日期、顺序号或“当前版本 / 最新版本 / 生效版本”等文字判断最新版。
- 若出现冲突，优先采用文档明示结论，其次结合版本号与日期判断，并在结果中注明冲突。
- 提取该版本记录中的变更摘要。
- 优先根据颜色标注 Markdown 中的 `bg` / `fg` 标签识别该版本记录所使用的颜色；必要时再用视觉理解复核，包括高亮底色、字体颜色、边框颜色、批注色块、表格底纹及其他可见标记。
- 同一份文档会进行多个版本修改，每次可能使用不同的颜色，**不要**对颜色进行任何假设。仅根据最新版本的版本记录所使用的实际颜色，去对应正文中本版本的变更内容。避开文档中可能存在的颜色描述误导，如：“不同部分已标红”等表述。
- 若当前版本记录没有可辨识颜色，明确记录“未发现可用色标”，随后退化为基于版本记录文字描述的人工对位整理；不要臆造颜色结论。
- 若当前版本记录同时使用多个颜色，先判断这些颜色是否分别指向不同变更类别；无法判定时，保留歧义说明。

### 2. 扫描全文并提取本次版本的新增或修改

- 优先扫描颜色标注 Markdown 中的颜色标签；必要时再使用视觉理解逐页扫描正文、表格、流程图、备注、脚注、嵌图和批注区域。
- 仅将与当前版本色标一致，或明显属于同一色系且承担相同修订语义的内容，认定为本次版本新增或修改。
- 将其他颜色标记视为其他版本遗留信息；将未标色内容视为背景信息。
- 以实际着色范围为准，不要仅因相邻而扩大变更范围；段落中只有局部着色时，只提取着色片段及其必需上下文。
- 对导出压缩、透明度变化、浅深差异造成的轻微色偏，可视为同色；对明显不同色相，不要合并认定。
- 若同色内容呈现删除线、替换说明、废弃标记或“原规则取消 / 调整为”之类表述，将其整理为“旧规则废止 + 新规则生效”的实现说明，不要把互斥规则并列保留。

### 3. 补足与本次变更直接相关的背景规则

- 阅读与变更项相邻或被其引用的未标色规则，恢复本次改动的完整语义。
- 仅保留实现所必需的背景信息，例如对象定义、前置条件、状态约束、流程入口、数值口径、配置来源、异常处理和权限边界。
- 对与本次功能实现无直接关系的世界观、叙事包装、美术描述或历史说明，避免大量带入结果文档。
- 若背景规则与本次变更存在冲突，优先以本次变更为准，并把冲突点列入“待确认项”。

### 4. 重写为程序实现文档

- 按 `implementation-doc-template.md` 的结构组织结果。
- 先给出“版本识别结果”和“本次变更摘要”，再进入功能设计正文，避免直接跳到代码细节。
- 将策划语言改写为程序可执行规则，补齐触发条件、输入输出、状态变化、数值约束、异常路径、配置项和联动对象。
- 对每条规则注明来源：`本次变更`、`背景沿用` 或 `推断`。若使用推断，必须说明推断依据。
- 最终产物必须体现“修改后的当前有效规则”，而不是只罗列 diff。
- 将最终文档保存到当前项目 `docs/desgin/` 目录中的 Markdown 文件。

## 判定准则

### 版本判断

- 版本记录区存在明确“当前 / 最新 / 生效”标识时，优先采用该标识。
- 若只有多个版本条目且没有明示说明，优先采用排序最靠后且版本号最高的条目；若仍有歧义，再结合日期判断。
- 若文档出现正文版本号与首页版本记录不一致，优先信任版本记录区，并在结果中注明冲突。

### 色标判断

- 先从版本记录区确定目标颜色，再回到正文搜索同色内容；不要先扫全文再反推颜色。
- 表格单元格底色、边框色、字体色、批注泡泡、旁注标签、流程框颜色，都可作为有效色标。
- 同一页中若相同颜色既用于版本修订又用于普通强调，只有同时满足“颜色一致”与“语义属于修订”的内容才计入本次变更。

### 歧义与退化处理

- 若文档没有版本变更记录，但存在明显统一色标，可按色标提取本次变更，并明确说明“版本号未锁定”。
- 若既没有版本记录，也没有稳定色标，则退化为普通策划案转实现文档流程，并声明未完成版本差异识别。
- 若视觉质量过低、颜色难以区分、截图被压缩或批注遮挡，先给出低置信度提示，再列出需要人工确认的部分。

## 输出要求

- 面向 gameplay 程序员写作，重点回答“要实现什么、何时触发、状态如何变化、数据如何配置、客户端与服务端如何分工、边界怎么处理”。
- 对新增内容写成完整的新规则；对修改内容写明修改后现行规则，并在必要时补一句“相较旧版的变化”。
- 保留必要的原始词汇映射，如玩法名词、系统名、字段名、枚举名、活动阶段名。
- 对缺失信息不要擅自补全为确定事实；可给出最小必要推断，并进入“待确认项”。

## 禁止事项

- 不要把所有带颜色的内容一并视为本次修改。
- 不要忽略未标色但对理解变更必不可少的背景规则。
- 不要仅输出摘要、会议纪要或改动列表。
- 不要把策划案原文大段搬运到结果里而不做程序化整理。
